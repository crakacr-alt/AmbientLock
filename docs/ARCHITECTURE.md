# Архитектура AmbientLock

Этот документ объясняет проект не как «магический инструмент», а как обычную
последовательность маленьких шагов.

## 1. CLI

`cmd/ambient/main.go` почти пустой. Это сделано специально: `main` трудно тестировать,
поэтому настоящая логика находится в `internal/app`.

## 2. Наблюдение

`internal/trace.Runner` запускает команду через `strace -ff`.

Почему `-ff`:

- дочерние процессы получают отдельные trace-файлы;
- строки разных процессов меньше перемешиваются;
- parser проще и надёжнее.

v0.1 наблюдает:

- `execve` — какой executable реально запустился;
- `open`, `openat`, `creat` — какие файлы удалось открыть;
- `connect` — к каким endpoint процесс попытался подключиться успешно или через
  обычный non-blocking `EINPROGRESS`.

## 3. Parser

`internal/trace/parser.go` превращает текст `strace` в `Observation`.

Важный принцип: если строка не распознана надёжно, мы её игнорируем. Лучше
недосчитать capability и явно записать ограничение в документации, чем придумать
ложный результат.

## 4. Model

`internal/model` описывает формат `ambient.lock`.

`Normalize()` сортирует и удаляет дубликаты. Благодаря этому два одинаковых
запуска не создают бессмысленный шум в Git diff.

## 5. Contract diff

`internal/contract` сравнивает baseline и новый запуск как множества.

Для `diff` важны и добавления, и удаления.

Для `enforce` критичны только **новые** capabilities. Если старая зависимость
исчезла, это обычно не повод ломать CI.

## 6. Почему v0.1 не блокирует syscall

`strace` хорошо подходит для понятного учебного MVP и наблюдения, но preventive
sandbox требует другой модели. Для реальной блокировки filesystem в Linux лучше
смотреть в сторону Landlock, а для syscall policy — seccomp.

Поэтому v0.1 сначала строит правильный контракт и тестовую базу. Preventive layer
добавляется позже отдельным backend-ом.
